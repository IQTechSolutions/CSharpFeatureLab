# Design: Episode 20 Server-Side Invitation Delivery

Generated by /office-hours on 2026-08-31
Branch: main

Mode: Builder

## Problem Statement

Episode 19 deliberately reveals a raw workspace-invitation code to Blazor once. That
is safer than making the code repeatable, but the browser still receives a bearer
capability that can grant membership. Episode 20 must honour the promised next slice:
issue the invitation on the trusted server, hand its raw code directly to a dedicated
delivery boundary, and return only non-secret metadata to the browser.

## What Makes This Cool

The visible result is subtraction. The owner still enters one recipient email and sees
an honest delivery outcome, but the raw code disappears from the HTTP response, client
result types, component state and rendered markup. Integration tests recover the code
only from a controlled delivery test double and use it to accept the invitation once,
proving the feature still works end to end without exposing the capability to Blazor.

## Constraints

- The lesson must fit 6-10 minutes and leave the .NET 10 solution compiling and tested.
- Tenant scope and current-owner authority continue to come from trusted server state.
- The database continues to retain only the invitation-code hash.
- The raw code must not enter HTTP responses, URLs, logs, telemetry, browser storage,
  Hangfire arguments or repeatable invitation-list results.
- Episode 20 teaches the delivery boundary, not SMTP, a vendor SDK, templates, an
  acceptance-link format, a durable outbox or retry infrastructure.
- Development and tests may use a thread-safe recording delivery implementation that
  is inspectable only through dependency injection. It must expose no debug endpoint
  and must remove a recorded delivery when a test consumes it.
- Startup outside Development and Testing must require an explicitly configured
  delivery adapter. It must never silently discard an invitation or log its code.

## Premises

1. Episode 20 should continue Episode 19's explicit server-side-delivery preview.
2. A successful browser response needs safe issuance metadata and an honest delivery
   status, not the bearer code.
3. The validated recipient passed to delivery must come from the server issuance
   result, not from the endpoint's raw request value.
4. Persisting an invitation and contacting an external delivery system is a dual write:
   two state changes that cannot share the current database transaction.
5. This episode uses explicit best-effort compensation after delivery failure and must
   report when compensation is uncertain. Durable, retryable delivery belongs to
   Episode 21's protected transactional outbox.

## Approaches Considered

### Approach A: Boundary First

Selected. Add a server-only delivery contract and application coordinator, remove the
code from the public contract and compensate after delivery failure. This is the
smallest slice that fulfils the prior lesson's promise.

### Approach B: Protected Outbox First

Rejected for Episode 20 because Data Protection, a new migration, durable dispatch,
Hangfire processing and retry rules would overload one beginner lesson. This remains
the Episode 21 destination.

### Approach C: Concrete Provider First

Rejected because credentials, provider configuration and network behaviour distract
from the trust boundary while leaving the same persistence-versus-delivery gap.

## Recommended Approach

### Server-only contract

Add `ITenantInvitationDelivery` under the server tenancy feature with this exact shape:

```csharp
Task DeliverAsync(
    Guid invitationId,
    string recipientEmail,
    string code,
    DateTimeOffset expiresAt,
    CancellationToken cancellationToken);
```

Normal task completion means the adapter accepted the handoff. It does not claim inbox
arrival or recipient use. Avoid a positional record whose generated `ToString()` would
print the secret. Implementations must never log or stringify the recipient and code.

Add `TenantInvitationDeliveryService.IssueAndDeliverForOwnerAsync(...)` between the
endpoint and `ITenantInvitationStore` with this signature:

```csharp
Task<IssueAndDeliverTenantInvitationResult> IssueAndDeliverForOwnerAsync(
    string userId,
    string securityStamp,
    long membershipVersion,
    Guid trustedTenantId,
    string requestedRecipientEmail,
    CancellationToken requestCancellationToken);
```

The identity, membership version and tenant identifier come from claims and the trusted
tenant context. The store validates the requested recipient. The result is one of
`HandedOff`, `InvalidRecipient`, `ActiveMember`, `Conflict`, `StaleOwner`,
`DeliveryFailedCompensated` or `DeliveryOutcomeUnknown`. Only `HandedOff` carries the
non-secret invitation identifier and expiry. The coordinator owns this sequence:

1. Reuse the existing owner-authorised issuance operation.
2. Stop immediately for invalid recipient, conflict, stale owner or active member.
3. For `Issued`, pass the server-validated recipient, raw code and expiry to
   `ITenantInvitationDelivery` inside the server process.
4. Use a linked delivery token with a ten-second server timeout. Normal completion
   returns `HandedOff` with only the invitation identifier and expiry.
5. On adapter exception or cancellation after issuance, call
   `CloseUndeliveredAsync(tenantId, invitationId, compensationToken)` with an independent
   five-second server timeout.
6. Map `Closed` to `DeliveryFailedCompensated`. Map `NoLongerOpen`, timeout or database
   failure to `DeliveryOutcomeUnknown` and emit one sanitized critical event containing
   only an event identifier and the non-secret invitation identifier.

Issuance itself uses the HTTP request token. Cancellation before the store returns an
`Issued` result causes no delivery attempt. If the store returns `Issued` while the
request token is already cancelled, the coordinator skips delivery and runs the same
server-timed compensation. A cancellation or exception before the store reveals the
result can leave the commit outcome unknown; no success is claimed, the event contains
no recipient or code, and the owner reconciles through the safe pending list. The
protected outbox in Episode 21 is the durable fix for this remaining commit window.

`ITenantInvitationStore.CloseUndeliveredAsync` targets only the just-created invitation
under the trusted tenant, and only while it remains open. It is idempotent: it returns
`Closed` when this call closes the row and `NoLongerOpen` when another action already
accepted, cancelled or closed it. It never accepts browser-supplied tenant, recipient or
code values. Compensation is best effort, not a guarantee.

### Honest failure semantics

The endpoint returns `201 Created` with
`TenantInvitationHandedOffResponse(Id, ExpiresAt, DeliveryStatus)` only after the
adapter completes normally; `DeliveryStatus` is exactly `handedOff`. Both delivery
failure outcomes return `503 Service Unavailable`, and neither the exception nor the
code enters the response. They use Problem Details with the safe extension
`deliveryStatus: "deliveryFailedCompensated"` or
`deliveryStatus: "deliveryOutcomeUnknown"`. The first tells the owner to retry. The
second tells the owner to refresh the pending list and cancel any remaining invitation
before retrying. `ActiveMember` and `Conflict` both map to the existing generic 409 body
so the public contract does not reveal membership state.

An external adapter can time out after the provider accepted the message. Successful
compensation then invalidates a code the recipient may still receive, unless the
recipient accepted it first. Compensation can also fail, leaving an active invitation
whose code cannot be reconstructed. The UI and HTTP result must describe these states
honestly instead of claiming fail-closed or exactly-once delivery. Episode 21 removes
the persistence-versus-delivery gap with a protected transactional outbox.

### Safe browser contract

Remove `Code` from the client success result and delete the one-time-code fields and
markup from `PendingInvitationsPanel`. Map the exact `handedOff` response to a typed
client outcome. On success, show "Invitation handed to the delivery service" and
refresh the existing code-free pending list. Preserve the current rule that a failed
safe-list refresh does not reverse a successful command.

### Development and test delivery

Use a singleton, thread-safe recording implementation only in Development and Testing.
It stores at most 100 entries in a `ConcurrentDictionary<Guid, ...>`, keyed by
invitation identifier. `TryTake(id)` atomically returns and removes only that test's
entry and rejects any entry older than five minutes. A `TimeProvider`-backed periodic
cleanup removes expired entries within 30 seconds even while the host is idle. Capacity
exhaustion fails the handoff instead of evicting an unknown secret. It exposes no HTTP
surface.

`Program.cs` registers this recorder only for Development and Testing. For every other
environment, it registers no fallback. Immediately after `builder.Build()` and before
middleware or endpoints are configured, `Program.cs` resolves
`ITenantInvitationDelivery`; a missing registration throws an
`InvalidOperationException` during host startup. This companion lesson intentionally
ships no silent no-op or pretend production adapter.

## Test Plan

1. A current owner receives a safe success response and exactly one delivery is
   recorded for the server-validated recipient.
2. The recorded raw code hashes to the stored value and can accept the invitation once.
3. The POST response, client result, rendered component, pending-list response and
   captured application logs never contain the raw code.
4. Invalid input, anonymous access, non-owner access, stale ownership, active membership
   and duplicate invitation conflict record zero deliveries.
5. A delivery failure with successful compensation returns a generic 503, closes the
   invitation, makes its attempted code unusable and permits a fresh retry.
6. Compensation timeout, database failure and a concurrently accepted/cancelled row
   return the distinct safe `DeliveryOutcomeUnknown` path, log no recipient/code and
   direct the owner to refresh before retrying.
7. HTTP cancellation after issuance still uses the independent compensation timeout.
8. Concurrent duplicate issuance produces one open invitation and at most one
   successful delivery.
9. The recorder's keyed `TryTake`, five-minute access limit, scheduled cleanup and
   capacity limit prevent parallel tests from consuming or retaining another test's
   secret.
10. Client tests map both exact Problem Details delivery-status values without exposing
    provider exceptions or the raw code.
11. A Production host without an adapter fails during startup, while a Production host
    with an explicitly registered test adapter starts successfully.
12. Existing invitation acceptance, cancellation, listing and Blazor refresh tests stay
   green.

## Open Questions

No Episode 20 scope decision remains open. Provider choice, protected payload format,
outbox schema, retry policy, delivery templates and operational metrics are explicitly
deferred.

## Success Criteria

- The owner can submit the existing Blazor form and receive an honest safe outcome.
- No public or browser-side contract contains the raw invitation code.
- The server-only adapter is invoked once per successfully issued invitation attempt.
- The stored invitation remains hash-only and the delivered code accepts exactly once.
- Delivery failure returns a secret-free, truthful compensated-or-uncertain outcome;
  the owner retries only after compensation succeeds or the pending list is reconciled.
- Restore, formatting, Release build and all focused/full tests pass with no warnings.
- The lesson script can explain the slice, dual-write gotcha and proof in 6-10 minutes.
